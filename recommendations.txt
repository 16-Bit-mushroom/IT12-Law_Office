# 🔍 **GENERAL SYSTEM OBSERVATIONS**

You are building a law office information system. The biggest risk here is **fragmentation** — having clients, payments, transactions, and documents duplicated across Notarial, Cases, and Legal Consultations.

You avoid that by doing **unification where it matters**:

* One **Clients** table
* One **Transactions** table (with "type" field)
* One **Payments** table referencing Transactions
* Each module (Notarial / Cases / Consultation) links to a *Transaction Item* (optional)

This keeps reporting, accounting, auditing, and UI consistent.

# ================= Notarial Entries Page =================

### ✔ Thoughts

### **1. "Entry not added to transaction — why?"**

Because *not all notarial acts are billable*, or sometimes the lawyer/staff encodes entries first then enters payment later.

Better rule:

* **Every notarial entry can have a transaction**, but it may start **Unpaid**.
* The transaction is created automatically when the entry is added.

### **2. Should you add a Pay button?**

✔ Yes
It makes workflow faster.
Workflow:

* If entry has no transaction → Show **"Create Transaction"**
* If transaction exists but unpaid → Show **"Pay"**

### **3. Should parties in a notarial entry be added to clients?**

Opinion: **No.** Keep “Clients” minimal.
Notarial parties are often one-time names (affiants, witnesses).
Do *not* clutter the Clients table with random individuals.

Clients page = people relevant to **Cases** and **Consultations**.

Use one table — cleaner backend, easier filtering.
